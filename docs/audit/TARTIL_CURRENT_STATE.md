## 1. How to read this document

Status vocabulary (project standard): **WORKING**, **PARTIALLY WORKING**, **UI ONLY**, **BROKEN**, **MISSING**, **BLOCKED**, **NEEDS SCHOLARLY REVIEW**. A status means "the code path exists and has the stated evidence", never "a user has used it". "n/a" means the column does not apply. "not verified" means I could not confirm it and will not guess.

Evidence rules used in the matrix:
- **Test Coverage** names the test file(s) that reference the route (found by a static search of `packages/api/test` and `packages/database/test`; a reference is not proof that every branch is asserted). "Browser E2E: none" means no repeatable browser test exists in the repository for that function. `packages/api/e2e/a11y-audit.mts` and `scripts/e2e_academy.mjs` are manual scripts, outside `npm test`.
- **Accessibility** is only ever "axe 0 violations (Chromium)" where a QA document records it, or "not verified". No screen-reader pass, keyboard-only walkthrough, real-device or Safari/iPhone test is recorded anywhere (docs/09_VISUAL_QA.md, docs/10_FUNCTIONAL_QA.md, docs/governance/KNOWN_LIMITATIONS.md section 35).
- **Database Integration / live state** comes from migrations in `packages/database/migrations` (0001-0017) and PROJECT_STATE.md / KNOWN_LIMITATIONS.md. I did not query the production Supabase project, so "live" claims are "per docs, not verified by me".
- Priority: **P0** = blocks an honest pilot or is a safety/truthfulness risk; **P1** = needed for a pilot to be useful; **P2** = quality; **P3** = later.

Deployment facts that affect many rows (per PROJECT_STATE.md and KNOWN_LIMITATIONS 37-40, not verified live): migrations 0001-0015 applied to Supabase; the deployed edge function is v22 and does **not** contain the plan routes (0015), kids routes (0016) or formation routes (0017); migration 0016 and 0017 are not applied. The SPA is served from Vercel (`packages/web-vercel/vercel.json` rewrites `/api/*` to the Supabase function). `packages/web/index.html` is a second copy that differs from `web-vercel` only in the `api-base` meta tag (4-line diff).

## 6. Observations that cut across rows

1. **Server features with no UI**: formation engines (0017). **UI with no server**: Academy lessons/scenarios/progress and the review portal (static JSON + localStorage), Foundations progress, Tajweed library. Progress for these lives on one device and is invisible to teacher or parent.
2. **Unreviewed teaching content is the largest honesty risk.** Tajweed, qiraat, quizzes, foundations, track templates and the whole Academy are AI-authored drafts. Each is labelled in the UI; none has a recorded review, because no `scholarly_reviewer`, `pedagogical_reviewer` or `child_protection_reviewer` exists.
3. **Deployed vs repository drift**: plan, kids and formation routes are tested in the repository but not in the deployed edge function (per docs). Anything on the live site that calls them will fail until the owner authorises a redeploy.
4. **Browser coverage is thin**: no browser E2E is committed; journeys A-G from the owner brief have no repeatable browser test (docs/10). Logged-in pages were checked with a mocked API.
5. **`packages/web` and `packages/web-vercel` carry duplicate 1,918-line SPAs.** Only the API base differs; they can drift.
