# TARTIL 14.1 - Academy publication backend (items 13-14)

Status: built and tested at database and API level. NOT applied to production. The web UI does not use it yet.

## What exists
- Migration `packages/database/migrations/0020_academy_content_status.sql` (0019 belongs to the progress work).
  - `academy_content_status` (kind program|lesson|scenario|guide, ref, version, status, cycle, created_by, updated_by, timestamps; PK kind+ref+version).
  - `academy_content_reviews` (type source|scholarly|pedagogical|child_safety, reviewer, decision approved|needs_revision, note, cycle). Immutable, never deleted.
  - Lifecycle: Draft -> Source Review -> Scholarly Review -> Pedagogical Review -> Child Safety Review -> Approved -> Published; Needs Revision (from any review stage, Approved, Published; returns to Draft); Archived (terminal; from Draft, Needs Revision, Approved, Published).
- API `packages/api/src/academy-content.ts`, registered in `app.ts` (one import, one call):
  - `GET /academy/content/status` public, published rows only, no identities (optional `?kind=`).
  - `GET /academy/content/status/all` reviewers only (403 otherwise), optional `kind`, `status`.
  - `POST /academy/content/:kind/:ref/transition` body `{version, to}`. `to: "draft"` on an unknown item registers it as a new draft.
  - `POST /academy/content/:kind/:ref/review` body `{version, reviewType, decision, note?}`; `needs_revision` requires a note.
- `scripts/seed_academy_status.py`: writes `docs/human-formation/academy_status_seed.json` (24 programs, 255 lessons, 136 scenarios, 24 guides, all Draft, with their current `review_status`). It writes a file only and touches no database.

## Rules enforced in the database (not only in the API)
1. Publishing (and Approved) requires an approval of each of the four types, in the item's current cycle, from four DISTINCT users who still hold the matching active role and are not the author. Checked again on every move to Approved and to Published, so a forced or stale state still cannot publish.
2. Leaving a review stage forward requires that stage's approval. Stages cannot be skipped.
3. Role mapping: source = scholarly_reviewer or pedagogical_reviewer; scholarly = scholarly_reviewer; pedagogical = pedagogical_reviewer; child_safety = child_protection_reviewer. Reviews are accepted only while the item is in the matching stage; a reviewer can only write a review as himself; the author cannot review; one person cannot give two review types on the same item and cycle.
4. A `needs_revision` decision moves the item out of review at once. Returning to Draft starts a new cycle, so earlier approvals no longer count.
5. RLS (forced): anyone, including signed-out, reads `published` rows only; holders of a reviewer role read all. Reviews are reviewer-only. app_user cannot delete, cannot write created_by/cycle/updated_by, and `app_user` remains non-superuser without BYPASSRLS. Deleting is refused even for the owner (archive instead).
6. No approval row is ever generated by this work; the seed contains only Draft entries.

## Limits (plain)
- Test coverage: `packages/database/test/academyContent.test.ts` (8 tests) and `packages/api/test/academyContent.test.ts` (2 tests) pass; `tsc --noEmit` is clean for both packages. Only these two files were run, not the full suite.
- There is no separate "editor" role. Editors are holders of a reviewer role (scholarly, pedagogical or child_protection), who are appointed by the owner (0018 blocks tenant admins from granting them). Until such people are appointed nothing can be moved or published. Any reviewer-role holder may perform transitions, including publishing; there is no distinct publisher role. Needs the owner's decision.
- Approvals bind to (kind, ref, version), not to a content hash: the content is static JSON outside the database. Changing a text must be done as a new version, which the process cannot enforce by itself. Content is not checked against the JSON files (a ref need not exist there).
- Publishing a status row does not itself publish the text: the web UI and static content do not read this table yet, and the licence/launch decisions remain the owner's.
- Requiring four distinct people means at least four appointed people: one scholarly, one pedagogical, one child-protection, and a fourth scholarly or pedagogical reviewer for the source review.
- Migration 0020 has not been applied to any live database.
