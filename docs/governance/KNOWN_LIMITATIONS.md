# KNOWN_LIMITATIONS (honest list)

1. **No user interface yet.** API slice 1 exists (tested on PGlite); `pg.ts` adapter is untested against a live Postgres/Supabase. No rate limiting, email verification, password reset, MFA, refresh tokens, or token revocation yet - login tokens last 1 hour and cannot be revoked.
2. **Quran text: Tanzil Uthmani only (Hafs)**, not religiously approved; no other riwayat. Citation check uses a consonantal skeleton ignoring alef/hamza (orthography differs between Uthmani rasm and the books), so it can accept near-misses; ~5% of quotes remain unmatched. Re-running scripts/generate_registry_docs.py overwrites the manually appended citation section of the review queue - re-run verify step after it.
3. **Triage is title-based**, validated only by term density; no scholar reviewed it. 9764 is uncertain.
4. **No printed page numbers** in the source exports; citations to "page X" cannot be produced - only section/paragraph locators.
5. **Source typos exist** (8 ayah numbers out of range, ~23 unresolved surah names); flagged, not corrected.
6. **Dedup is textual** (4-word shingles, MinHash): it can miss paraphrase and can over-link formulaic phrases. Thresholds (0.80/0.55) are my choice, uncalibrated against scholarly judgement. Oversized-bucket guard never triggered on this corpus.
7. **Tests run on PGlite (PostgreSQL 18 WASM)**, not a managed Postgres. Role switching (`SET LOCAL ROLE app_user`) must be re-verified on the chosen host (e.g. Supabase/Neon/RDS) before any deployment. No penetration test performed.
8. **Context injection** (`app.user_id`, `app.institution_id`) is trusted from the API layer; a compromised API server could set any value. Mitigation (signed context / per-request JWT claims) is a future ADR.
9. **Safeguarding** covers data access + consent only. No messaging, no live-session controls, no reporting workflow yet. Legal review of child-data rules per jurisdiction: not done.
10. **QCEF** seed (105 items, from the previous kit) is uncalibrated scaffolding; not loaded into the DB, not scholar-reviewed.
11. **AIJUR Skills** was not available and was not inspected.
12. Canonical Jazariyya/Tuhfa witness text undecided (queue Q-003).
13. Normalisation for matching is crude (diacritics/hamza/ya/ta-marbuta) and is never applied to stored text.

## Added with migration 0008 (tracks, certificates, sessions, AI, account security)
14. **No email provider**: password recovery by email does NOT exist. Only change-password (knowing the current one) and logout-all. A locked-out user needs the institution admin; an admin reset flow is not built.
15. **No LLM connected**: the AI assistant endpoints exist and are tested with a fake model only; live they answer `model_not_connected` (501). Suggestions are drafts, hidden from students until a human accepts (enforced by RLS). Connecting a model needs the owner's key/terms/cost decision and a child-data review (consent purpose `ai_analysis`).
16. **Live halaqat = external Jitsi room link** (meet.jit.si, unguessable per-session token, opened 15 min before start). Not recorded by the platform, no in-platform moderation, the public Jitsi service is a stopgap with no SLA. Minors need a verified guardian link (checked), but nobody can technically stop a leaked link from being shared. Real video infrastructure is an owner cost/design decision.
17. **Sessions**: 1 h JWT, revocable via logout-all / password change (checked on every authenticated request through `users.sessions_valid_after`). No refresh tokens, no device list, no MFA.
18. **Registration** requires an "18+" self-confirmation (a checkbox, not age verification). Minors are created by their guardian/institution as student profiles; guardian verification is a manual admin step. Not legal advice; per-jurisdiction review (COPPA/GDPR-K etc.) not done.
19. **Certificates** are course-completion records of an institution (all units of a published track marked done by an assigned qari, issued by tenant_admin). Not an ijazah. Public verification shows no name for minors. No PDF/printable certificate yet, no revoke endpoint (column exists).
20. **Concept extraction (makharij/sifat)** is lexical, ~15% of sampled units were false/tangential (see docs/extraction/CONCEPTS_V1.md). Output is DRAFT, licence-not-cleared, metadata only; nothing is published.
21. **UI** was exercised with headless Chromium against a local PGlite-backed server (register/adult checkbox, track create/publish, account dialog, guardian consent before/after verification). The microphone recorder and the live Supabase+Vercel UI path were not click-tested by me.

22. AI assistant is connected to an external model (OpenAI, `gpt-4o-mini`, key held as the Supabase secret OPENAI_API_KEY, never in the repo). Only the free-text prompt is sent (no user identity); output is a PENDING draft that a human must accept. Sending any student content to a third party is the owner's data-protection decision; minors' data must not be sent until that is decided. Tested live with one adult smoke account (deleted).
23. The web client was rebuilt (2026-11-01 evening) from an admin console into a product UI: public landing, full Quran reader (114 surahs, names, search, bookmarks, resume), role dashboards (student/qari/admin/guardian), names instead of UUIDs (`/people`, `/sessions-upcoming` endpoints). Surah names are a static client list (checked against the live ayah counts for 10 surahs, not all 114). Reader search runs in the browser after downloading the surahs (no server-side index). Bookmarks/last-read are per browser (localStorage). Not browser-tested: microphone recording and upload, a real Jitsi join, Safari/Firefox. Tested headless (Chromium) against the live Quran data and a local DB for account flows.

24. **Tajweed library and track templates are AI-authored and provisional.** The `#/tajweed` section (makharij, sifat, ahkam, mudood, letter explorer) and the three ready track templates were drafted by the platform's AI from commonly agreed tajweed knowledge (Hafs 'an 'Asim). Quran examples are fetched from the approved edition and checked against it (16/16 refs resolve); the explanatory text has NOT been reviewed by Al-Azhar/Haramain scholars and is labelled "under scholarly review" in the UI. The template payloads are verified by an API test (all three accepted, saved as draft tracks); the button itself was not clicked in a browser.

25. **Personal learning space (hifz, quizzes, mastery map, PWA) is self-assessment.** Migration 0009 adds per-user tables (RLS: own rows only). Review ratings, quiz scores and the "memorised" status are the learner's own and are NOT a qari's assessment, a grade or an ijazah. The four quizzes (makharij, sifat, noon/meem rules, mudood) are AI-authored and pending Al-Azhar/Haramain review. The service worker caches the app shell and public Quran text only; it was not tested on a real phone. Streak days use UTC dates server-side. Not built yet: qiraat/ijazah tooling, scholarly-review UI, tajweed colouring, audio of reciters (licences not cleared), translations/tafsir (licences not cleared), email delivery.

26. **Scholarly review workspace and sanad register (migration 0010).** Only an active `scholarly_reviewer` (membership in any institution) can read/move scholarly items; the DB trigger still forbids illegal transitions, requires an active reviewer as approver, and refuses PUBLISHED until the OWNER sets `licence_cleared` (deliberately not settable from the UI). No reviewer has been appointed yet, so nothing has been reviewed and no extracted content is published. The sanad register is self-declared; "verified" means a reviewer (never the holder) recorded having seen the supporting documents; the platform issues no ijazah. The qiraat page is a provisional introduction (AI-authored, pending review); only Hafs text is loaded.

27. **Tajweed colouring is an approximate, rule-based display layer (provisional).** It never changes the stored text (verified: all 6236 ayat reconstruct byte-for-byte). It classifies ghunna, ikhfa, idgham (with/without ghunna), iqlab, qalqala (sukun only) and extra madd (maddah sign). It does NOT cover: izhar, idgham mithlayn within a word, madd types separated, qalqala at waqf, rules that change when stopping or by riwayah, nor any sifat-based rules (tafkhim/tarqiq, ra/lam rules). Waqf signs block cross-word rules conservatively. Needs a scholarly reviewer's audit before it is presented as reliable; off by default.
28. **Curriculum templates are proposals, not endorsed curricula.** The eight ready-made tracks (foundation reading, Tuhfat al-Atfal, al-Jazariyyah, Juz' 29 and 28 memorisation, selected surahs, weekly review, 30-day khatm) follow the commonly taught graded sequence of traditional halaqat. They were authored by AI and are NOT approved, endorsed or issued by Al-Azhar, the Haramain or any other body. They are created as drafts and must be reviewed by an appointed scholarly reviewer before an institution publishes them. The khatm template is checked to cover all 6236 ayat exactly once; the juz' boundaries follow the standard Madinah mushaf and should be confirmed by the reviewer.
29. **Institution admin console (roster, suspension, stats, audit trail).** Admin-only endpoints `/roster`, `/members/:id/status`, `/overview-stats`, `/audit-trail` check the caller's active `tenant_admin` role inside the RLS context; the sole remaining admin cannot be suspended. Suspension blocks access to institution data through RLS but does not delete the membership, and existing tokens remain valid for the user's other institutions. There are no email invitations (a member must already be registered), no billing, and the audit trail shows object types and actors, not field-level diffs.
30. **English translation is provisional.** The Clear Quran edition (Talal Itani, CC BY-ND 4.0) is stored in separate immutable tables, never mixed with the Arabic text, and shown only as an opt-in reader toggle with attribution and a disclaimer. Approval is the owner's provisional one; no scholarly reviewer has examined it. The ND licence forbids altering the wording, so it is displayed verbatim. English only, one edition (the "Allah" variant); no other languages, no tafsir.
31. **Recitation audio is streamed from a third party with unstated terms.** The reader plays surah audio and highlights the current ayah using mp3quran.net's public timing data (Hafs 'an 'Asim reciters only). The service publishes no licence; we do not store or alter the audio. It depends on that service being online and keeping its URLs, the browser's autoplay rules apply, and per-ayah highlighting is missing for reciters/surahs without timing data. Not tested with a real screen reader, on iOS Safari or on a mobile network. Recordings are not part of the Quran text layer and are not scholarly-reviewed.
32. **Tafsir panel depends on a public repository with unstated data licence.** Five classical tafsirs are fetched per ayah from jsDelivr / raw.githubusercontent. They may be unavailable if the repository moves or rate-limits; some ayat have no own entry (merged with a neighbour); the digitised text is not verified against printed editions or scholarly-reviewed; long entries (al-Tabari) are shown whole in a scrollable box. A tafsir is a study reference, never a ruling. No tafsir is stored in our database; no search across tafsir.
33. **Whole-Quran search is simple substring search.** Arabic search ignores diacritics and the alef/ya/ta-marbuta variants and finds a contiguous phrase inside an ayah (no root/lemma search, no word-order tolerance, no ranking); it shows the first 50 matches. English search is a case-insensitive substring match in the Clear Quran translation. Results always show stored text verbatim. It searches one edition (the first approved) and runs a full scan of about 6,000 rows per query, which is fine at this size but is not an index.
34. **Tajweed colouring and letter joining on WebKit (iPhone/Safari).** WebKit cut Arabic joining at the edge of every coloured inline element, so coloured letters looked detached. The display layer now puts a zero-width joiner on both sides of a styled boundary, only where the two letters really connect (dual-joining letter before any letter except hamza). It never touches stored text; removing the joiners gives the original text (tested). Side effect: copying coloured text from the page carries invisible joiners. The fix was verified in Chromium only; it has NOT been verified on a real iPhone, which is where the defect was reported. If it persists there, the fallback is to switch colouring off (it is off by default) or to colour by whole words.

34b. Tajweed colouring now paints character ranges with the CSS Custom Highlight API (Safari 17.2+, Chrome 105+, Firefox 140+), leaving the verse as one plain text node so no word is split. Colour tooltips are not available on this path (the legend is). Older browsers fall back to coloured spans with joiners (limitation 34 applies). Verified in Chromium only; iPhone result is for the owner to confirm.
